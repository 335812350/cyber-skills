## 1. 背景：从「重 Harness」到「轻约束」

早期（GPT-5.4 / Opus 4.6 阶段）靠 Superpowers 这类重 Skill 提供 Spec + TDD 流程，确实能提高
完成质量。代价是 token 消耗快：流程写死了下一步，即使从全局看某一步已经没必要，模型仍会
沿着流程继续跑。

模型能力增强后，原本有用的约束开始变成噪声。作者的做法是**定期给工作流做减法**——
例如新模型发布后，删掉 `AGENTS.md` 里一些过严的约束。

## 4. 常用 Prompt：思维快捷键

作者已经很少手写大段 Prompt，转而使用短句指定「方法论」。理由：这些方法论在训练数据里
已经高度标准化，模型见过大量相关论文、代码和设计文档。

| 方法 | 典型说法 | 模型行为的转变 |
|---|---|---|
| 第一性原理 | 「不要基于既定方案继续优化，重新问这个问题到底该怎么解」 | 从「Redis 怎么设计」转为「瓶颈在 SQL、网络、序列化还是锁」 |
| 对抗性审查 | 「不要帮我的方案找理由，想办法证明它是错的」 | 从「锁超时设多少」转为「重复请求真的需要互斥吗？幂等能不能解决？」 |
| 消融实验 | 「给这几个优化设计消融实验，判断真正的收益来自哪里」 | 设计 Baseline / 单变量 / 多变量对照，找出真正贡献 |
| 奥卡姆剃刀 | 「删除所有非必要机制」 | 把 Kafka + Redis + 分布式锁 + 状态机 + 定时补偿 收敛成一个事务 + 唯一索引 |
| 高内聚低耦合 | 「审查职责边界，不要为了拆而拆」 | 判断哪些逻辑属于领域本身，哪些应通过稳定接口外移 |

组合使用即五种认知动作：重新定义问题 → 攻击假设 → 验证贡献 → 删除复杂度 → 整理边界。

作者的建议是：与其写死一套思考流程，不如用准确的方法论告诉模型「应该以什么方式思考」，
再补充当前任务真正必要的约束。

## 5. 日常工作流

1. **喂上下文 + 对齐**：PRD、会议纪要、聊天记录、用户反馈 → 结合 Wiki 和现有代码理解 →
   连续追问目标、边界、取舍。
   停止条件：剩下的问题不会显著改变实现方向和验收结果。
2. **沉淀**：结论写入 Spec / `CONTEXT.md`，记录问题、范围、关键决策、验收标准。
3. **执行**：简单需求直接做；复杂需求拆成边界清楚、可独立验收的 Issue；只有能独立推进的
   部分才交给 subagent 在不同 worktree 并行，主 Agent 负责集成。
4. **自测**：编码 Agent 先完成测试。
5. **交叉审查**：按复杂度引入其他 Agent 做对抗性审查，问题统一回给主编码 Agent 修复。
6. **端到端测试**，然后人工 Review。

人工 Review 不逐行读代码，主要看测试结果和核心业务逻辑。前提是**每次 MR 都足够小**，
并在开发推进过程中逐步验证完整业务路径。

## 6. Agent 友好的端到端测试

问题：AI 很擅长写测试（动辄几百行），但上线后仍会遇到预期之外的错误。原因是没给 Agent
一个端到端环境，让它有机会在编码和自测阶段就发现问题。

搭建方式：提炼日常自测流程，把散落的能力集成起来——能工具化的做 MCP 或 CLI，可复用的
流程写成 Skill。四件事：

1. 让 Agent 熟悉环境：一键启动、造数、明确版本/账号/权限、清理与重置。
2. 让 Agent 能操作业务系统：浏览器、API 或 CLI。
3. 让 Agent 能查库表和日志：只读数据库 MCP 确认落库，日志 Skill + Trace 定位链路。
4. 把繁琐但稳定的流程复用起来：脚本 + Skill + 统一测试 CLI。

几个具体做法：

- **浏览器自动化**：ego lite 开源浏览器，配 pi + DeepSeek V4 Flash 跑得快。
- **统一 CLI**：整合 Skill、MCP、脚本，提供环境检查、数据准备、场景执行、结果查询、清理。
- **让工具服务于验收**：DB 查状态、日志和 Trace 解释失败，但**预期结果必须来自业务契约**，
  不能让 Agent 看到系统返回什么就认为什么是对的。
- **产品本身是 Agent 时**：还要评估答案质量（Agent Eval）。

## 7. Code Review 实践

- 先看验收标准，再看测试结果；不只看通过数，看测试是否验证了这次需求真正关心的事。
- 沿业务路径看实现，重点放在权限、状态变化、并发、重试、数据一致性、迁移与回滚。
  稳定的 CRUD 可以少看甚至不看。
- 新增的抽象和机制，单独用奥卡姆剃刀再审一遍。
- MR 多时可以做专门的 Review Bot：结合 Git 变更信息和预设审查流程，形成可重复执行的审查能力。
  评价标准是**是否减少有效问题的遗漏和人工负担**，不是评论了多少条。

## 8. 反思

- **瓶颈是 Review 速度，不是生成速度。** Agent 能并行推进多个任务，但人理解业务、判断方案
  的速度不会成倍增加；只让 Agent 写得更多，结果往往是积压更多待审代码。
- 改进方向：让重复问题在交到人手里之前被发现——能被类型检查、测试、业务断言捕获的，
  让 Agent 在开发过程中自己处理；需要人判断的，集中在需求是否理解对、关键业务逻辑是否成立、
  以及还有哪些没有验证的风险。
- **Harness 的完整理解**：不只是给 Agent 正确的上下文，还要给它**能执行任务的环境**和
  **判断结果的依据**。
- 工作流要定期做减法：区分简单任务和复杂任务，模型变了就重新判断某些步骤是否还有收益。
- 测试和 Review 只能降低不确定性：代码和测试可能一起误解需求；端到端测试只覆盖选定环境和
  场景，生产环境的流量、并发和数据分布仍会带来新问题。**人仍然要负责给出正确的验收标准。**
- AI 减少了一部分亲自踩坑的机会，作者会专门留出时间学习和复盘。

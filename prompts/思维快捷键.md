# 思维快捷键

> 五句方法论 Prompt。复制粘贴即可用，不需要安装任何东西。
>
> 来源：黄同学h《入职大厂两个月，我的 AI 开发心得》·

## 为什么是这几句

模型训练时见过大量论文、代码、设计文档，这些方法论本身已经高度标准化。所以不需要手写
几百行 Workflow，只需要告诉它**采用哪套思考方式**。

这些 Prompt 不是魔法咒语，它们的作用是切换模型的注意力：从"怎么实现既定方案"切到
"这个方案该不该存在"。

---

## 1. 第一性原理

**什么时候用**：怀疑"题目本身可能就问错了"；方案是别人给的，或者沿用了很久但没人验证过。

**通用模板**

```
不要基于「<当前既定方案>」继续设计。从第一性原理分析这个问题，以及最小必要的解决方案。
```

**原文示例**

```
不要基于「加 Redis 缓存」这个既定方案继续设计。从第一性原理分析这个接口为什么慢，
以及最小必要的解决方案。
```

**模型会怎么变**：不再回答"Redis 怎么设计"，而是追问瓶颈在 SQL、网络、序列化、锁竞争
还是重复计算；如果加个索引就能解决，为什么还要引入 Redis。

---

## 2. 对抗性审查

**什么时候用**：方案评审、Code Review、准备把一个设计交给别人实现之前。

**普通问法**（效果差）

```
帮我看看这个技术方案有没有问题。
```

**换成**

```
对这个方案做一次对抗性审查，优先寻找能推翻核心假设的反例。
```

**原文示例**：方案是"为了解决重复请求，引入分布式锁"。

模型不再讨论锁的超时时间，而是追问：

- 重复请求真的需要互斥吗？
- 接口幂等能不能解决？
- 锁服务挂了怎么办？
- 锁过期了但业务还没执行完怎么办？
- 是不是为了解决一个局部问题，又引入了新的分布式故障点？

---

## 3. 消融实验

**什么时候用**：一次做了多个优化，不确定收益到底来自哪一个；或者准备保留一堆复杂机制。

**通用模板**

```
给这几个优化设计消融实验，判断真正的收益来自哪里。
```

**原文示例**：加索引 + Redis 缓存 + 批量查询后，接口耗时从 800ms 降到 100ms。

让模型以 Baseline 为起点设计对照：只加索引 / 索引 + 缓存 / 索引 + 缓存 + 批量查询。

可能的结果：

> 只加索引就已经从 800ms 降到 120ms，剩下两个复杂方案只贡献了 20ms。

这样才知道哪些代码值得保留、哪些复杂度可以删掉。

---

## 4. 奥卡姆剃刀

**什么时候用**：设计里堆了太多机制；Agent 给你的方案"看起来很完整"；Review 时怀疑过度设计。

**通用模板**

```
用奥卡姆剃刀重新审查这个设计，在满足需求的前提下删除所有非必要机制。
```

**原文示例**：Agent 给出的方案是 `Kafka + Redis + 分布式锁 + 状态机 + 定时补偿`。

模型可能发现：当前场景只有单库写入，**一个事务加唯一索引就够了**。

这条对现在的 Coding Agent 尤其有用——模型很容易为了"完整"而过度设计。

---

## 5. 高内聚低耦合

**什么时候用**：单个类/服务过大；职责开始混在一起；准备拆分模块之前。

**通用模板**

```
按高内聚、低耦合原则审查 <类名/服务名> 的职责边界，不要为了拆而拆。
```

**原文示例**

```
按高内聚、低耦合原则审查 OrderService 的职责边界，不要为了拆而拆。
```

**模型会怎么变**：它会检查为什么订单服务同时负责库存、优惠券、短信、支付和报表；
哪些逻辑属于订单领域本身，哪些应该通过稳定接口交给其他模块。

它激活的不是"拆文件"，而是一整套关于模块化、信息隐藏、依赖方向和职责划分的判断。

---

## 组合用法

与其写"第一步分析需求，第二步检查假设……"，不如一句话指定五种认知动作：

```
从第一性原理重新分析，对当前方案做对抗性审查；核心机制必须通过消融实验验证；
方案遵循奥卡姆剃刀，代码保持高内聚、低耦合。
```

对应：

> 重新定义问题 → 攻击假设 → 验证贡献 → 删除复杂度 → 整理边界

## 配套 Skill

这些 Prompt 负责"怎么想"，技能负责"怎么执行"。按阶段配：

| 阶段 | 配套 Skill | 怎么配 |
|---|---|---|
| 需求还没对齐 | [`grill-me`](https://github.com/mattpocock/skills/tree/main/skills/productivity/grill-me) | 先用它把目标、边界、取舍问出来，再进入方案 |
| 方案设计 / 判断值不值得做 | [`think`](https://github.com/tw93/Waza/tree/main/plugins/waza/skills/think) | 产出决策完整的方案，而不是给你列选项 |
| 方案评审 / Code Review | [`check`](https://github.com/tw93/Waza/tree/main/plugins/waza/skills/check) · [`code-review`](https://github.com/mattpocock/skills/tree/main/skills/engineering/code-review) | `check` 对照验收标准；`code-review` 并行查规范和 spec 符合度 |
| 清理过度设计 | [`ponytail`](https://github.com/DietrichGebert/ponytail) | 实现完成后跑，专门砍多余抽象 |
| 模块边界设计 | [`codebase-design`](https://github.com/mattpocock/skills/tree/main/skills/engineering/codebase-design) · [`domain-modeling`](https://github.com/mattpocock/skills/tree/main/skills/engineering/domain-modeling) | 设计深模块、划边界、沉淀术语表/ADR |
| 消融实验 | 无现成 Skill | 需要真实可跑的性能测试环境，用脚本做多组对照 |

完整工作流见 [../ai-dev-workflow/SKILL.md](../ai-dev-workflow/SKILL.md)。

## 一个反例

不要这样写：

```
第一步分析需求，第二步检查假设，第三步寻找替代方案，第四步评估风险，第五步输出方案……
```

这是把模型当成不会思考的执行器。模型已经知道这些步骤；真正需要你指定的是：
**这次用哪种思考方式，以及这次任务特有的约束是什么。**

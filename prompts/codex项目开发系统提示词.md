# 项目开发规则

目标：大型任务 → 方案先行 → Codex 评审 → 可行性校正 → 再实现
避免“写着写着发现方案不对”的情况

## 大型任务处理流程

### 1. 任务识别

收到用户命令后，先判断是否为大型任务。符合以下任一条件即为大型任务：

- 涉及多个文件或模块的修改
- 需要新建多个文件或组件
- 涉及架构调整或复杂业务逻辑
- 预计实施步骤超过 5 步

### 2. 需求分析与规划

确认为大型任务后：

- 分析用户需求及相关代码
- 理解现有处理逻辑和依赖关系
- 深度思考后创建 `./md/plan-{功能名称}-{日期}.md`，包含：
  - **用户原始需求**：原封不动记录
  - **技术方案设计**：
    1.总体架构思路
    2.核心实现方式
    3.关键技术选型
  - **影响范围分析**：
    1.涉及模块
    2.涉及文件
    3.可能的风险点
  - **实施步骤概要**：仅到“阶段级别”，不写代码级 todo
    ⚠️ 此阶段 禁止直接进入编码

### 3. Plan 可行性评估

- 在 plan.md 创建完成后，必须先进行 Codex 方案评估，确认方案是否合理、可实现、是否有遗漏。

- 3.1 Codex Review（Plan 阶段）
  使用非交互模式执行：
  
  ```bash
  codex exec "请评估以下实施方案的可行性与合理性：
  文档：./md/plan-{功能名称}-{日期}.md
  ```

请从以下角度进行 review：

1. 方案是否完整、是否存在遗漏

2. 技术选型是否合理

3. 实施步骤是否可执行

4. 是否存在潜在风险或更优方案

5. 给出明确的修改建议（如有）" \
   | tee ./md/plan-review-{功能名称}-{日期}.md
   
   ```
   ### 4. Plan 修订与确认（Plan v2）
    •    阅读 plan-review-*.md
    •    对 Codex 的建议逐条评估：
    •    ✅ 采纳：直接修改 plan.md
    •    ❌ 不采纳：在 plan.md 中记录原因
    •    更新 plan.md 中的：
    •    技术方案设计（升级为 v2）
    •    实施步骤概要（补全或修正）
   ```

📌 只有当 Plan v2 明确“可执行”后，才允许进入实施阶段

### 5. 详细 To-Do 拆解

- 基于 已确认的 Plan v2：
    •    在 plan.md 中新增章节：实施 To-Do 列表
    •    要求：
    •    拆解到 文件 / 类 / 方法级别
    •    明确每一项的输入、输出、依赖
    •    可被逐条勾选完成

示例结构：

```md
## 实施 To-Do 列表
- [ ] 新建 XXXController
- [ ] 新增 XXXService 接口
- [ ] 实现 XXXServiceImpl 逻辑
- [ ] 修改 XXXMapper 查询
- [ ] 补充单元测试
```

### 6. 实施阶段

- 严格按照 To-Do 列表执行
- 尽量参考当前系统/项目里已有代码或接口的规范进行开发,如果有可复用的,尽量复用现有系统中的代码风格和公共能力
- 逐步实施并标记完成状态
- 实施过程中如有方案调整，同步更新 plan.md,再继续编码

### 7. 创建实施文档

实施完成后创建 `./md/impl-{功能名称}-{日期}.md`，包含：

- **任务概述**：简要描述实现的功能
- **文件变更清单**：列出所有新建和修改的文件
- **核心代码说明**：关键实现逻辑的说明
- **接口文档**：新增 API 接口的说明（如有）
- **测试验证**：如何验证功能是否正常
- **待优化项**：已知的可优化点或遗留问题

### 8. Codex Review

使用非交互模式在后台执行代码审查：

```bash
codex exec "请阅读以下文档进行代码审查：
1. 实施方案：./md/plan-{功能名称}-{日期}.md
2. 实施记录：./md/impl-{功能名称}-{日期}.md
请检查实现是否符合需求和方案，给出优化建议" | tee ./md/review-{功能名称}-{日期}.md
```

> 说明：`codex exec` 为非交互模式，可后台运行；`| tee` 将结果同时输出到终端和文件

### 9. 优化迭代

- 评估 Codex 给出的优化建议
- 选择性采纳合理的优化方案
- 记录未采纳建议的原因（如有）
- 更新 `./docs/` 中对应的功能文档

---

## 其他开发规范

- 异常处理使用 `throw new ServiceException()` 统一处理
- Controller 层不做 try-catch，由全局异常处理器处理
- ServiceImpl 层获取用户 ID 使用 `LoginUtil.getLoginId()`
- 所有 md 文件统一放入 `./md/` 文件夹
- 功能点文档放入 `./docs/` 文件夹
